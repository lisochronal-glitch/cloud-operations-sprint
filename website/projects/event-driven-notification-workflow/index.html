AWS Event-Driven Workflow Project

Event-Driven Notification Workflow

A SaaS application needs to process notification events without making the main application wait for the work to finish.

This planned project will use SNS, SQS, Lambda, dead-letter queues, and CloudWatch to build a reliable asynchronous workflow with failure handling and operational visibility.

SCENARIO

Asynchronous notification processing for a SaaS application

The application publishes events such as signup notifications, payment status updates, or account activity messages. These events should be processed outside the main request path.

The workflow should queue messages reliably, process them with Lambda, retry temporary failures, move repeated failures to a dead-letter queue, and provide logs and metrics for operational troubleshooting.

PLANNED ARCHITECTURE

SNS fanout with SQS buffering, Lambda processing, and DLQ failure handling

Application event
  ↓
SNS Topic
  ├── SQS processing queue → Lambda processor → CloudWatch Logs
  └── SQS audit queue

Failure path:
SQS processing queue
  ↓
Dead-letter queue

AWS SERVICES

Services planned for this lab

  • Amazon SNS for publishing application events
  • Amazon SQS for buffering notification jobs
  • A second SQS queue for audit fanout
  • A dead-letter queue for repeated processing failures
  • AWS Lambda for message processing
  • CloudWatch Logs and metrics for operational visibility
  • CloudFormation for repeatable deployment and cleanup
